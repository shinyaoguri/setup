# グローバル CLAUDE.md

全プロジェクト共通の個人規約。実体は setup リポジトリの `claude/CLAUDE.md`
(settings.json とあわせて tasks/claude.yml が `~/.claude/` 配下へシンボリックリンク)。
プロジェクト・リポジトリ固有の規約は各所の CLAUDE.md / CONTRIBUTING.md が正本で、
ここでは繰り返さない。

## 全作業共通

- 応答・説明は日本語 (settings.json の `language` が主、ここは確認用)。成果物の言語は用途と指示に従う
- 品質を最優先する。結論だけ要る調査や読み取り中心の独立作業はサブエージェントへ切り出し、メインコンテキストを本題に温存する。委譲は高性能モデルが既定で、結果が変わらない定型作業のみ安価なモデルへ (迷ったら高性能側)
- やり直しがきく作業は、経過と根拠を残しながら指示を待たず進めてよい。不可逆な操作・外部へ影響が及ぶ操作 (送信・公開・共有・削除・履歴の書き換えなど) だけは事前にユーザーへ確認する。ただし**可逆と確認できたものは自分で判断して進める** (マージ済みローカルブランチの掃除など、内容が remote や main に残っていて取り戻せるもの)。git の破壊的操作は PreToolUse フック (`claude/git-safety-guard.sh`) がリポジトリの状態から可逆性を判定して allow / ask / deny を返すので、**フックが通した操作を改めて聞き直さない** (可逆と確認できたブランチ掃除は allow で確認プロンプトごと出ない)
- ユーザーに問うのは、技術的な正解が導けず**意図に依存する選択**のときに限る (どちらを選んでも成立し、コードにも規約にも答えが無い場合)。調べれば分かることは聞かずに調べ、判断が要るだけなら仮定を明示して進める
- **人間の確認は「実装に入る前のプラン」1 点に集約する**。非自明な実装 (複数ファイルに及ぶ・設計の選択肢がある・要件が曖昧) はいきなり書き始めず、まず EnterPlanMode で目的・変更点・確認方法を示して合意を取る。合意なしに編集が広がると repo-standards プラグインの `plan-gate` フックが deny で差し戻す。逆に、合意が済んだ範囲の可逆な作業では確認を求めない — 押すだけの確認を増やすと、本当に見るべき 1 回まで反射で押すようになる
- 実行時の安全は 4 層で担う: `permissions.ask` (必ず人間に返す = 取り返しのつかない削除だけ) / PreToolUse フック (`claude/*.sh`・プラグイン同梱の決定論的判定) / auto mode の分類器 (`settings.json` の `autoMode`。意味での判定) / `/env-doctor` (上 3 層が実際に効いているかの検査)。**分類器の設定はこの `claude/settings.json` にしか書けない** — プロジェクトの `.claude/settings.json` もプラグインも対象外で、リポジトリ側から自分に都合のよい許可を注入されないための公式仕様。「対象リポに置けばよいのでは」と提案しない
- セッションの記憶 (auto-memory 含む) はいつでもリセットされる前提。決定・発見・方針変更に加え、進行中の状況・課題・残タスク・調査の中間所見・検証ログも、その作業の恒久的な置き場 (開発なら Issue・PR とそのコメント・docs、それ以外なら該当ドキュメント等) へ積極的に記録する
- 複数ステップの作業は着手時に計画を宣言し、長い調査は中間結果をこまめに追記する。記憶ゼロからでも置き場を読むだけで状況把握・再開できる状態を保つ
- **着手時に立てたプランも置き場へ残す** (開発なら PR・Issue のコメント)。プランは `~/.claude/plans/` にも溜まるがローカルのマシンにしか無く、PR 本文に書かれるのは結果であって着手時点の前提・却下案ではない。plan-record.sh が持ち出せる形 (絶対パスとホームディレクトリを畳み、秘密情報があれば止める) に整えて投稿コマンドまで示すので、**他の開発者が読む前提で本文を確かめてから投稿する** — 自分の環境でだけ成り立つ手順や、相手に不要な個人情報は落とす。投稿しないまま終えようとすると Stop hook が差し戻す
- 問題・ミス・手戻りが起きたら、応急処置で終わらせず、同じ問題を繰り返さないための改善策もあわせて検討・提案する
- 改善策の手段は CLAUDE.md への追記に限らず、hooks・スクリプト・CI・利用ソフトやサービスの設定まで多角的に比較し、根本原因に効く最もシンプルな一手を選ぶ。決定論的に強制できる仕組み (hooks・lint・CI 等) を文書ルールより優先する
- 個別の対症ルールを積み増して全体を肥大させない (個別最適より全体最適)。置き場は問題のスコープに合わせる (プロジェクト固有はそのリポジトリへ、全プロジェクト共通のみここへ)
- 秘密情報・個人情報・実データの置き場は gitignore 済みの `.env` などに限り、成果物・ログ・外部サービスへ不用意に持ち出さない。代わりにダミー値・環境変数名・参照 (パスや ID) だけを渡す (コミット混入は git-safety-guard フックが deny で強制ブロック)
- **1Password の秘密は `op read` ではなく `secret-read <参照>` で読む**。無人セッション (hook・scheduled task・バックグラウンド) はロック解除に応えられず黙って止まるので、単一用途で失効が容易な秘密だけ Keychain にキャッシュして読めるようにしてある。何を許すかは setup の `secret-cache-allowlist` が正本で、SSH 鍵やアカウント認証は載せない (承認プロンプトが出ること自体が防御)。状態は `secret-read --check`、ローテート後は `secret-read --refresh <参照>`
- スクリーンショット等の画像読み込みはトークン高コスト。検証はまずテキストベース (DOM・状態・ログの読み取り) で進め、視覚チェックは人間へ依頼する。画像を読むのは他の手段で理解できないときに限る (完成度は妥協しない)
- GUI を伴う作業 (画面・見た目・動き・操作手順) を Issue・PR に記録するときは視覚的な証跡を積極的に添える。見た目には静止画、**動きが分からないと正誤を判定できないもの (アニメーション・遷移・インタラクション・時間依存の描画) には GIF も**。**リポジトリに画像・GIF をコミットせず** Gyazo へ上げて URL を貼る (手順は gyazo-capture スキル)

## ソフトウェア開発

- コードの識別子は英語。コメント・ドキュメント・コミット要約は日本語でよい
- GitHub Flow: main が唯一の長命ブランチ。作業は main から `<type>/<短い説明>` ブランチを切り、小さく作って早めに PR (WIP なら Draft)
- **着手した Issue には `status: in progress` を付け、PR が merge されたら / 中断したら外す** (ラベルが無いリポでは `gh label create` で作る)。複数のセッションが同じリポで並行するので、着手は push を待たずに GitHub 側から見える必要がある。次のタスクを選ぶときはこのラベルが付いた Issue と、in-flight PR が触っているファイル群を避ける — 収集から着手までの手順は repo-standards プラグインの next-task スキルが持つ
- コミットは Conventional Commits: `<type>(<scope>): <要約>`。type は feat / fix / docs / refactor / test / chore / ci。1 コミット 1 関心
- Squash merge 前提。PR タイトルもコミットと同形式に書く (マージコミットのメッセージになる)
- コミットログと PR 本文 (目的・変更点・確認方法) を丁寧に書くこと。それが書けていて CI が green なら、push / merge は指示を待たず進めてよい (force push・main への直接 push は上記の不可逆操作として事前確認)
- **マージを起点にリポジトリが自動で走らせる後続処理はマージに含まれる** (リリース・タグ・パッケージ公開・デプロイなど)。「公開だから」を理由に確認を挟まず、規約どおりの PR ならマージまで一続きで進めて結果を報告する。自動化の有無と bump 規則はリポジトリの規約・ワークフロー定義から読み取る。人が明示的に起こす公開操作 (手動の `workflow_dispatch`・手動タグ・外部への告知) は上記の不可逆操作として事前確認
- merge 後は main に戻って pull する。**ローカルブランチの掃除は Stop hook が `git gone-clean` で自動的に行う**ので、自分で `git branch -D <名前>` を打たない (追跡先が畳まれる前に打つと safety guard が ask を返し、人手の確認を要求してしまう)。その場で消したいときは `git gone-clean` / `git stale-clean` を使う — 状態を変えるコマンドなので allow には置かないが、safety guard が「gone なブランチだけを消す」と読めるため確認は出ない
- **Issue / PR へのコメントは本文の末尾に署名を付けて投稿する**。同じ場所に人間も複数のエージェントも書き込むので、発言の出どころが後から辿れる必要がある (ChatGPT Codex は GitHub App 経由の投稿なので GitHub が「commented with 〜」を描くが、ローカルの gh CLI から投稿する Claude Code にその表示は出ない)。水平線を挟んで次の 1 行 — 付け忘れは gh-comment-guard フックが差し戻す:

  ```markdown
  ---
  <sub>🤖 Assisted by [Claude Code](https://claude.com/claude-code)</sub>
  ```

- 1 PR = 1 関心事。本題以外のバグ・改善に気付いたら直接修正せず、`gh issue list --search` で重複を軽く見てから `gh issue create` で起票
- 仕様・設計 docs は叩き台として扱い、曖昧点・軽微な矛盾は同一 PR で docs も改訂して根拠を残す。確定要件・設計判断級の変更は事前にユーザーへ確認する
- テストは実装 PR に含める: バグ修正は失敗する再現テストが先 / 正常系に加えて失敗系・境界値を最低一つ / 新しいテストは検証対象の振る舞いを一時的に壊して赤くなるのを見てから仕上げる (壊しても緑のままのテストは書き直す)
- スキルは用途で置き場を分ける: 複数プロジェクトで使う汎用スキルは自作 marketplace (shinyaoguri/claude-plugins) のプラグインとして配布し、特定プロジェクト固有のものは各リポジトリの `.claude/skills/` へ。第三者配布スキルもコピーせず plugin marketplace 経由で入れる。いずれも settings.json で宣言し (extraKnownMarketplaces / enabledPlugins)、`~/.claude/skills/` には実体も symlink も置かない
